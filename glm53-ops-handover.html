GLM-5.3 推理集群运维手册

两台 H20 服务器各自完整运行一份 GLM-5.3，第三台机器上的网关统一接收请求，并优先转发到已缓存相同前缀的机器。本文写清楚各服务在哪、怎么启停、怎么扩容、出问题怎么查，以及哪些配置不能动。

对外地址 http://10.10.93.89:8000 监控 http://10.10.93.89:3000 模型名 glm-5.3

概况

模型精度FP8权重 704G，KV 缓存也是 FP8

所有镜像都在 registry.cn-hangzhou.aliyuncs.com/ripper/ 下。推理镜像 sglang-runtime:latest 的内容与 NVIDIA 官方 nvcr.io/nvidia/ai-dynamo/sglang-runtime:1.5.1 一致。

  • 两份独立副本：两台机器互不依赖，各自能处理完整请求。一台宕机，另一台继续服务，只是总吞吐减半。
  • 按缓存路由：每台推理节点把自己缓存了哪些前缀实时上报给网关。网关综合缓存命中长度和当前负载，选出最合适的机器，同一会话的后续请求通常会落在同一台上。
  • 两级缓存：显存放不下的 KV 缓存会转存到主机内存（HiCache）。每台机器在内存里额外能存约 290 万 token 的前缀缓存，命中时不用重新计算。
  • 自动上下线：推理节点启动后自己去 etcd 注册。进程退出后，大约 10 秒内注册失效，网关不再往它转发请求。
  • 缓存不持久：推理节点重启后，显存和内存里的缓存全部清空，需要重新预热。模型权重在本地硬盘上，不受影响。
网关机目前是单点

etcd 和网关都只部署在 10.10.93.89 一台机器上。这台机器宕机，整个服务就不可用，推理节点本身不受影响。这台机器上还运行着约 20 个其他业务容器，变更前要注意别影响它们。

网关机上的分词器文件必须和推理节点一致

网关负责把对话拼成提示词并分词，用的是 /data/glm-5.3/ 下的文件。以后如果推理节点更换了模型或聊天模板，要把这 9 个文件重新复制到网关机，再重启网关。

机器上的旧容器

h20-01 上原有的 gpustack、lmcache 等 8 个旧容器已停止，重启策略改为 no，开机不会再拉起。它们会抢占 GPU，不要再启动。h20-02 上有一个已停止的 gpustack-worker，它的重启策略仍是 unless-stopped，同样不要启动。

调用方式

接口兼容 OpenAI，地址 http://10.10.93.89:8000/v1，模型名 glm-5.3。目前没有 API Key 校验，内网任何人都能调用，客户端的 Key 字段随便填即可。

curl http://10.10.93.89:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "glm-5.3",
    "messages": [{"role": "user", "content": "你好"}],
    "reasoning_effort": "high",
    "stream": true,
    "stream_options": {"include_usage": true}
  }'
参数 / 字段说明
reasoning_effort思考强度，只认 low 和 high。不传或传其他值（包括 medium）都按最高档 max 处理，思考最长、最慢。模型没有关闭思考的开关，enable_thinking 参数无效。
思考内容放在返回的 reasoning_content 字段，正式回答在 content。
工具调用支持，按 OpenAI 的 tools / tool_calls 格式。
usage非流式请求总是返回。流式请求要传 stream_options.include_usage: true，会在最后多一个 choices 为空的数据块。命中缓存的 token 数在 usage.prompt_tokens_details.cached_tokens。
/v1/models列出可用模型。返回为空说明没有任何推理节点在线。

让缓存命中更高（给调用方的建议）

  • 提示词里固定不变的内容放最前面（系统提示词、工具定义），变化的内容（时间、用户信息、检索结果）放最后。系统提示词里只要开头出现一个变量，整段缓存都会失效。
  • 同一个业务固定用同一档 reasoning_effort。这个值会被写进提示词的第一行，切换档位等于换了前缀。
  • 多轮对话原样带上之前的消息，不要改写或删减历史。

日常操作

所有操作都在对应机器的编排目录里执行：推理节点和网关是 /opt/app/glm-5.3，指标采集器是 /opt/app/glm-5.3/exporters，监控是网关机的 /opt/app/glm-5.3/monitoring。

检查服务是否正常

# 任意机器：看本机容器状态，推理节点和网关应显示 (healthy)
docker ps --filter name=glm53

# 网关机：看当前在线的推理节点，正常是 2 行（每个节点 1 行）
docker exec glm53-etcd etcdctl get --prefix --keys-only v1/instances/dynamo/backend/generate

# 任意能访问网关的机器：接口是否可用
curl -s http://10.10.93.89:8000/v1/models

启动、停止、重启

cd /opt/app/glm-5.3
docker compose up -d                 # 启动（或在改了 .env / docker-compose.yml 后让改动生效）
docker compose restart               # 重启（改了 sglang.yaml 后用这个）
docker compose stop                  # 停止，保留容器
docker compose logs -f --tail 200    # 看实时日志
  • 启动顺序：先起网关机，再起推理节点。推理节点先启动也没关系，连不上 etcd 会自动重试，然后由 Docker 重新拉起。
  • 推理节点启动要等约 14 分钟。以 etcd 里出现这个节点为准，不要中途反复重启。
  • 停推理节点会比较慢：释放约 1.4TB 锁定内存需要一段时间，docker compose 可能提示超时。等一会儿再查容器状态，不要用 kill -9 或重启 Docker 硬处理。
  • 日志单个文件最大 100MB、保留 5 个，会自动轮转，不用手动清理。

修改配置

推理参数都在推理节点的 sglang.yaml 里，两台机器的这个文件必须保持一致。修改时一台一台滚动进行，保证另一台在线：

  1. 先备份：cp sglang.yaml sglang.yaml.bak，再修改 h20-02 上的 sglang.yaml。
  2. 在 h20-02 执行 docker compose restart，期间所有请求由 h20-01 承接。
  3. 等约 14 分钟，确认 etcd 里重新出现 2 个节点，再发一个请求验证。
  4. 把同样的修改复制到 h20-01，重复第 2、3 步。

滚动期间集群容量减半，被重启那台的缓存也会清空，所以尽量安排在业务低峰。

常改参数当前值说明
max-running-requests128每台同时处理的请求上限，超出的请求排队。调大时要同步调大 cuda-graph-max-bs。
context-length262144最大上下文长度（256K）。
hicache-size150每张卡在主机内存里的缓存大小（GB）。实际占用约 1.2 倍，8 卡共约 1.44TB。不能再调大，见“不要改的地方”。
chunked-prefill-size8192长提示词按 8K 一段分批计算，避免一个长请求卡住其他请求的输出。

新增推理节点

新节点只需要能连上网关机的 etcd，启动后自动加入，网关不用改任何配置。

  1. 硬件：8 张 H20-3e（141GB），内存不少于 2TB。内存小于 2TB 时，按比例调小 hicache-size。
  2. 环境：安装 Docker 和 NVIDIA Container Toolkit，Docker 设为开机自启。
  3. 模型：把权重完整复制到 /data/nvme0/glm-5.3（704G）。
  4. 编排文件：从 h20-02 整个复制 /opt/app/glm-5.3 目录（包括 .env 和 exporters），内容不用改。
  5. 镜像：拉取 sglang-runtime:latest、dcgm-exporter:4.2.3-4.1.3-ubi9、node-exporter:v1.9.1。
  6. 启动：在 /opt/app/glm-5.3 和 /opt/app/glm-5.3/exporters 下各执行一次 docker compose up -d。
  7. 确认加入：约 14 分钟后，在网关机用 etcd 命令查看在线节点，数量应该加 1。
  8. 加监控：在网关机的 monitoring/prometheus.yml 里，往 dynamo-backend、dcgm-exporter、node-exporter 三处各加一行新节点 IP，然后执行 curl -X POST http://127.0.0.1:9090/-/reload 让配置生效。

新节点和网关机之间网络要互通：新节点要能访问网关机的 2379 端口；网关机要能访问新节点的 5557 端口，以及 Dynamo 自动分配的请求端口。目前三台机器在同一内网，没有防火墙限制。

下线节点：在该节点执行 docker compose down，约 10 秒后网关不再往它转发；再从 prometheus.yml 里删掉对应 IP 并重新加载。

故障处理

现象先查什么处理
/v1/models 为空，或请求报找不到可用实例网关机上用 etcd 命令查在线节点；再到推理节点看 docker ps 和日志推理节点没起来就按下面几行处理。节点正常但 etcd 里没有它，重启该推理节点。
推理节点容器反复重启docker compose logs --tail 300，看最后的报错连不上 etcd：检查网关机 2379 端口和网络。GPU 被占用：用 nvidia-smi 找出并停掉占用的进程（多半是旧容器）。内存不足：见下一行。
推理机 SSH 很卡、ping 延迟高free -g 看可用内存主机内存基本被缓存占满。确认 hicache-size 没被调大（应为 150）。机器完全无响应时只能通过带外管理重启。
请求慢、超时引擎面板的排队数、首字延迟；调用方传的 reasoning_effort不传 reasoning_effort 时按最高档思考，复杂问题可能思考几分钟，调用方超时要设够长（已观察到 120 秒超时被客户端取消的请求）。排队数长期不为 0 说明容量不够，需要加节点。
两台机器负载不均引擎面板里各节点的运行请求数按缓存路由会让同一会话固定在同一台，短时间不均衡是正常的。只有一台有流量时，先确认另一台是否在线。
请求返回 400网关日志：在网关机执行 docker logs --tail 200 glm53-frontend多半是请求参数不合法，把日志里的报错原因转给调用方。
网关机拉镜像失败/etc/systemd/system/docker.service.d/ 下有没有代理配置该机器原来配了一个已失效的 Docker 代理，已删除。如果有人重新加了代理，确认代理可用。
etcd 容器被删除重建etcd 命令查在线节点etcd 数据没有挂载到宿主机，重建后注册信息全部丢失。推理节点能否自动重新注册未经测试。如果查不到节点，先重启网关，再逐台重启推理节点。

不要改的地方

下面这些都是部署时踩过坑或经过验证的设置，改之前务必先弄清原因。

hicache-size 不能超过 150

设置为 200 时，内存缓存加上索引的额外开销会占掉约 1.9TB（共 2TB），h20-02 几乎卡死，SSH 无响应。现在的 150 实际占用约 1.44TB，给系统留了余量。

DYN_FORWARDPASS_METRIC_PORT 必须为空

这是 NVIDIA 官方配方里的要求：该镜像的这项指标上报遇到第一个投机解码批次就会让调度器崩溃。不要删掉这一行，也不要给它赋值。

镜像用的是 latest 标签

如果有人往镜像仓库推送了新的 sglang-runtime:latest，执行 docker compose pull 会悄悄换掉版本。不要随手执行 pull，升级版本要作为单独的变更来做。

  • 启动参数里的 --dsa-prefill-backend flashmla_kv、--dyn-tool-call-parser glm47、--dyn-reasoning-parser glm45、--reasoning-parser glm45 是 GLM-5.3 需要的设置，改了会导致输出格式或工具调用出错。
  • sglang.yaml 里的 kv-events-config 是按缓存路由的数据来源，删掉后网关就无法按缓存选机器了。
  • 两台推理节点的 sglang.yaml 和 .env 要保持一致，否则同一请求在不同机器上表现不一样。
  • 不要启动 h20-01、h20-02 上的旧容器（gpustack、lmcache 等）。
